# 个人全维数据收集与量化系统 — 项目规划分析

> 文档版本: v1.0 | 日期: 2026-07-01 | 作者: 巴蒂塔洛

## 一、项目核心定位

这是一个**个人量化生活（Quantified Self）基础设施**。核心理念：

```
多端采集 → 统一汇聚 → 结构化存储 → 可视化回顾 → AI 理解与反馈
```

不只是一个"数据展示面板"，而是**让 AI 能够在不需要你描述的情况下，通过你的数据流理解你的状态**，主动提供提醒、建议和洞察。

## 二、需求全景图：所有数据类型的分类

按照你描述的数据，我用两个正交维度来划分：

### 维度一：数据形态

| 形态 | 说明 | 示例 |
|------|------|------|
| **当前状态 (State)** | 持续刷新覆盖，只保留最新值 | 当前地理位置、当前电量、当前正在使用的App、是否锁屏、是否在睡眠 |
| **持续统计 (Log)** | 累计追加，每条带时间戳，不可覆盖 | 应用使用时长记录、睡眠周期、账本交易、笔记修改历史、位置轨迹 |

### 维度二：数据源清单

| # | 数据类型 | 形态 | 来源端 | 数据量级 | 冗余/过期策略 |
|---|---------|------|--------|---------|-------------|
| 1 | **地理位置轨迹** | Log + State | Android (GPS) | 中（每1-5分钟一个点） | 保留全部，可降采样 |
| 2 | **PC应用使用时长** | Log | PC | 中 | 保留全部 |
| 3 | **手机应用使用时长** | Log | Android | 中 | 保留全部 |
| 4 | **PC/手机锁屏/解锁事件** | Log | PC + Android | 低 | 保留全部 |
| 5 | **睡眠时间** | Log | Android/手动/穿戴设备 | 低（每天1条） | 保留全部 |
| 6 | **账本（收支记录）** | Log | PC + Android | 低 | 保留全部 |
| 7 | **日目标 / 周目标笔记** | State + Log | PC + Android | 极低 | 保留全部，版本历史 |
| 8 | **日常拍摄（手机相册）** | Log | Android | 高（图片文件） | 同步缩略图+元数据；原图可选同步 |
| 9 | **Looki L1 录制** | Log | Looki L1 → PC | 极高（视频文件） | **核心冗余数据**：过期自动清理，保留元数据索引 |
| 10 | **设备在线状态** | State | 所有端 | 极低 | 心跳检测 |
| 11 | **天气/环境数据** | State + Log | 服务端拉取 | 低 | 保留全部 |

### 3.2 模块详细拆分

#### 模块 A：客户端采集层

**A1. PC 采集器**
- 功能：窗口/应用追踪、AFK检测、锁屏事件、外设插拔
- 复用方案：**ActivityWatch 的 aw-watcher-window + aw-watcher-afk**，直接将数据导向自建服务端
- 额外需要：自定义 aw-watcher 用于采集 ActivityWatch 不覆盖的数据

**A2. Android 采集器**
- 功能：应用使用时长、锁屏/解锁、电量、GPS位置、步数/健康数据（Health Connect API）、通知摘要、蓝牙设备连接状态
- 技术方案：原生Android App + 无障碍服务/UsageStatsManager + Health Connect API
- 关键约束：Android 后台限制严格，需要前台服务 + 通知栏常驻
- 参考：MyLifeTracker 的 AutoTask 方案（轻量但能力有限）

**A3. 第三方桥接器**
- 功能：从已有App/服务拉取数据
- 子模块：
  - 账本桥接：对接 Firefly III / Actual Budget 的 API
  - 睡眠桥接：对接 Health Connect (Android) 或 Apple Health
  - 笔记桥接：对接 Obsidian/Logseq 的本地文件变更监听
  - 位置回填：从 Dawarich 导入历史数据

**A4. 媒体导入器（PC端）**
- 功能：Looki L1 连接PC后自动导入视频/照片，提取元数据（时间、GPS、时长），生成缩略图
- 关键：原始媒体文件本地存储，只上传元数据到服务端；文件本身按过期策略清理

#### 模块 B：网络同步层

**B1. Tailscale 组网**
- 所有设备加入同一 Tailnet，形成虚拟局域网
- 服务端通过 Tailscale IP 暴露 API，无需公网IP、无需DDNS、无需HTTPS证书
- 优势：零配置内网穿透，端到端加密

**B2. 离线队列与同步**
- 每个客户端维护本地 SQLite 离线队列
- 有网时批量发送，无网时持续积累
- 同步协议：客户端发送 → 服务端确认（含去重ID） → 客户端清理已确认数据
- 冲突策略：服务端时间戳为准（Last Write Wins），客户端时间以服务端时钟校准

**B3. 同步频率控制**
- 可配置：实时推送 / 每分钟 / 每5分钟 / 每小时 / 仅在WiFi下
- 不同类型数据可设不同频率（位置高频，笔记低频，媒体仅WiFi）

#### 模块 C：服务端核心

**C1. 数据接收层**
- REST API：`POST /api/v1/data/{data_type}` 通用数据接入
- WebSocket：实时状态推送（当前App、位置、在线状态）
- 数据校验层：JSON Schema 验证，防止脏数据入库

**C2. 统一数据存储**
- PostgreSQL 主库：所有结构化数据
  - 核心表设计采用 **EAV（实体-属性-值） + 类型特化表** 混合方案
  - 详见第六节数据模型设计
- 文件存储：本地磁盘 / MinIO（照片缩略图、媒体元数据）
- 时间序列优化：TimescaleDB 扩展（可选，用于高频位置/使用时长数据）

**C3. 标签与分类系统**
- 每条数据统一携带标签：`{ timestamp, source, platform, data_type, form(state|log), redundant(bool), tags[] }`
- 标签支持层级：`activity.work`, `location.transit`, `media.looki`
- 冗余标记：自动计算（如视频超过30天标记为可清理）

**C4. 数据查询与透视**
- 通用查询API：按时间范围、标签、数据源组合查询
- 聚合API：日/周/月汇总，支持自定义时间窗口
- 导出API：JSON/CSV/Parquet 格式

**C5. 媒体管理服务**
- 媒体元数据索引
- 缩略图生成与缓存
- 过期清理调度（自动删除标记为 redundant 且过期的媒体文件）
- 存储空间统计

#### 模块 D：AI 上下文层

**D1. 数据提炼管道**
```
原始数据 → 时间窗口切分（日/周） → 统计摘要 → 结构化报告 → AI 上下文
```

**D2. 摘要生成**
- 每日摘要：活动时长分布、位置热力图、消费汇总、睡眠评分
- 每周摘要：趋势对比、目标完成率、异常事件标记
- 自然语言摘要：可由LLM生成，也可由规则模板生成

**D3. 异常检测**
- 睡眠异常：睡眠<5h或>10h
- 行为异常：应用使用时长远超平均
- 位置异常：长时间未移动或突然远距离移动
- 消费异常：单笔大额或日消费超阈值

**D4. 主动提醒引擎**
- 规则配置：条件 → 提醒内容 → 提醒方式（通知/语音/消息）
- 示例：
  - "连续工作90分钟" → "该休息了，站起来走走"
  - "晚上11点还在刷短视频" → "明天要早起，该睡了"
  - "本周运动时间不足2小时" → 周五提醒运动

**D5. AI 反馈接口**
- 将提炼后的数据上下文注入AI对话
- AI可以查询任意时间段的任意数据
- AI输出可触发提醒或生成报告

#### 模块 E：展示与交互层

**E1. Web 仪表盘**
- 当天概览：时间线视图（所有数据按时间排列的完整信息流）
- 应用使用：日/周/月分布图
- 位置地图：轨迹回放 + 热力图
- 财务状况：收支趋势 + 分类饼图
- 睡眠质量：周期图 + 趋势
- 目标追踪：完成率仪表盘

**E2. 全天信息流视图**
- 核心特色功能：将一天内所有数据事件按时间轴排列
- 例如：
  ```
  07:30  闹钟响起，解锁手机
  07:35  浏览微信 12分钟
  07:50  起床，开始移动（位置变更）
  08:00  打开电脑
  08:10  VS Code 使用中
  08:30  离开家（位置变更至地铁站）
  09:00  到达公司
  12:00  午餐消费 ¥35
  14:00  ...
  ```
- 支持缩放：从天级到分钟级
- 支持筛选：按数据类型过滤

**E3. 移动端 App**
- 轻量级：主要是数据仪表盘查看 + 快速录入（记账、笔记）
- 配置管理：调整同步频率、设备信息

### 5.2 数据模型设计（核心）

```sql
-- 核心事件表（通用日志型数据）
CREATE TABLE events (
    id          BIGSERIAL PRIMARY KEY,
    event_type  VARCHAR(64) NOT NULL,      -- 如 'app_usage', 'location', 'transaction', 'sleep'
    source      VARCHAR(64) NOT NULL,      -- 设备名: 'thinkpad-p1', 'pixel-8'
    platform    VARCHAR(16) NOT NULL,      -- 'pc', 'android', 'ios'
    form        VARCHAR(8)  NOT NULL,      -- 'state' | 'log'
    timestamp   TIMESTAMPTZ NOT NULL,
    end_time    TIMESTAMPTZ,               -- 用于持续事件（如睡眠、专注时段）
    payload     JSONB NOT NULL,            -- 灵活数据体
    tags        TEXT[] DEFAULT '{}',       -- 标签数组
    redundant   BOOLEAN DEFAULT FALSE,     -- 是否冗余（可清理）
    expires_at  TIMESTAMPTZ,               -- 过期时间
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- 索引优化
CREATE INDEX idx_events_ts ON events (timestamp DESC);
CREATE INDEX idx_events_type_ts ON events (event_type, timestamp DESC);
CREATE INDEX idx_events_source ON events (source);
CREATE INDEX idx_events_tags ON events USING GIN (tags);
CREATE INDEX idx_events_payload ON events USING GIN (payload jsonb_path_ops);

-- 当前状态表（只有最新值）
CREATE TABLE current_states (
    state_key   VARCHAR(128) PRIMARY KEY,  -- 如 'location:thinkpad-p1', 'app:pixel-8'
    source      VARCHAR(64) NOT NULL,
    value       JSONB NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL,
    UNIQUE(state_key)
);

-- 媒体元数据表
CREATE TABLE media_assets (
    id          BIGSERIAL PRIMARY KEY,
    source      VARCHAR(64) NOT NULL,      -- 'looki-l1', 'phone-camera'
    media_type  VARCHAR(16) NOT NULL,      -- 'video', 'photo'
    file_path   TEXT NOT NULL,             -- 本地存储路径
    file_size   BIGINT,
    duration    INTERVAL,                  -- 视频时长
    thumbnail   TEXT,                      -- 缩略图路径
    taken_at    TIMESTAMPTZ,               -- 拍摄时间
    location    GEOGRAPHY(POINT),          -- GPS位置（如果有）
    metadata    JSONB,                     -- EXIF等元数据
    redundant   BOOLEAN DEFAULT FALSE,
    expires_at  TIMESTAMPTZ,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- 每日摘要表（预计算，加速查询）
CREATE TABLE daily_summaries (
    date        DATE NOT NULL,
    source      VARCHAR(64) NOT NULL,
    summary_type VARCHAR(32) NOT NULL,
    data        JSONB NOT NULL,
    PRIMARY KEY (date, source, summary_type)
);
```

## 六、技术难点分析

### 难点 1：统一数据模型设计（★★★★★ 核心挑战）

**问题**：地理位置、应用使用、账本交易、睡眠记录、照片视频——数据类型差异巨大，字段完全不同。如何在"统一查询"和"类型特化"之间取得平衡？

**分析**：
- 纯 EAV 模型 → 查询慢，类型安全差
- 纯特化表 → 每种数据一张表 → 统一查询困难，cross-type关联几乎不可能
- **推荐方案**：主表 `events` 用 JSONB 承载 payload，特化表做高频查询优化
  - `events` 表负责**统一存储和跨类型查询**（时间线、全量搜索）
  - 为高频查询类型建立**物化视图**或**特化索引表**（如 `mv_app_usage_daily`）
  - `current_states` 表独立处理实时状态

### 难点 2：数据标签与透视系统的灵活性（★★★★）

**问题**：你希望数据可以按多种维度透视——日期、平台、类型、是否是冗余数据等。但这个标签体系需要在设计时就考虑清楚，否则后期改造成本极高。

**分析**：
- 标签系统需要支持：内置标签（自动打）+ 自定义标签（手动打）
- 内置标签在数据写入时自动计算：
  - `date:2026-07-01`, `hour:22`, `weekday:3`
  - `platform:android`, `source:pixel-8`
  - `form:log`, `redundant:false`
- 透视查询加速：对常用标签组合建立**部分索引**或**BRIN索引**
- **推荐**：PostgreSQL 的数组+GIN索引对标签查询足够快，不需要专门的标签系统

### 难点 3：离线收集与可靠同步（★★★★）

**问题**：Android 端在无网络时需要持续收集数据，有网后可靠上传，不丢数据，不重复。

**分析**：
- 客户端本地 SQLite 队列，每条约 200 字节
- 每条数据生成 `client_id`（UUID）用于去重
- 同步策略：
  1. 客户端发送批量数据 + 每条数据的 client_id
  2. 服务端检查 client_id 是否存在，存在则跳过
  3. 服务端返回 `{ accepted: [client_id...], duplicates: [client_id...] }` 
  4. 客户端清理已确认的数据
- **关键风险**：时钟偏差。Android 设备时间可能不准 → 解决方案：服务端返回 `server_time`，客户端记录偏移量
- **数据量估算**：假设每天 10,000 条事件，每条 200 字节 → 约 2MB/天，离线一周也仅 14MB，SQLite 完全够

### 难点 4：Android 后台采集的可靠性（★★★★）

**问题**：Android 系统对后台进程的限制越来越严格。持续的位置采集、应用使用监听可能被系统杀死。

**分析**：
- **应用使用时长**：`UsageStatsManager` 是系统API，不需要后台运行，定时查询即可（如每5分钟）
- **GPS位置**：前台服务 + 通知栏常驻是必须的。但持续GPS耗电严重
  - 折中方案：使用 `FusedLocationProvider` + 地理围栏 + 活动识别
  - 静止时不记录，移动时提高频率
  - 或直接用 Dawarich App（已解决此问题）
- **锁屏/解锁**：BroadcastReceiver 可能被限制 → Android 14+ 需要用前台服务
- **推荐**：优先用 Dawarich App 做位置（已经解决了Android后台问题），自建App只做应用使用时长、锁屏、电量等轻量采集

### 难点 5：媒体文件管理（★★★）

**问题**：Looki L1 录制的视频文件体积大（4K视频可能数GB/小时），全部上传不现实，但又要保留可回顾的信息。

**分析**：
- **元数据与服务端分离**：只上传元数据（时间、时长、GPS、文件名）+ 缩略图（~10KB）
- **原始文件策略**：
  - 默认保存在录制设备或PC本地
  - 标注 `redundant=true`，30天后自动提醒清理
  - 重要片段手动标记 `redundant=false`，永久保留
- **缩略图生成**：PC导入器用 ffmpeg 自动截取关键帧
- **不在 Tailscale 上传大文件**：Tailscale 不适合大文件传输。媒体文件走本地USB或局域网SMB

### 难点 6：AI 上下文的效率（★★★）

**问题**：如何把一天的几千条事件提炼成AI能理解的、有限的上下文？

**分析**：
- **不可能也不应该把所有原始数据都喂给AI**
- 三级提炼管道：
  1. **统计摘要**（规则生成）：时长分布、地点列表、消费总额 → 固定格式，~500 tokens
  2. **事件标记**（异常+关键）：异常行为、重要事件 → ~200 tokens  
  3. **自然语言摘要**（LLM生成，可选）：日常描述 → ~300 tokens
- 总计每天 ~1000 tokens 可用于AI上下文
- AI可以请求深入查询特定时间段或类型的数据（function calling）

### 难点 7：多系统集成的运维复杂度（★★★）

**问题**：ActivityWatch + Dawarich + Firefly III + 自建服务 → 四五个服务需要部署和维护。

**分析**：
- Docker Compose 可以统一编排
- 但每个子系统的升级、数据迁移、故障恢复都是独立的问题
- **渐进策略**：Phase 1 只用自建核心 + AW；Phase 2 加 Dawarich；Phase 3 加 Firefly III
- 各子系统通过API松耦合，任何一个挂了不影响其他

## 九、总结：一句话架构

> **以 PostgreSQL 为数据核心，ActivityWatch / Dawarich / Firefly III 为成熟的采集子系统，Tailscale 为网络层，自建 API 服务做统一调度，Web 仪表盘做可视化，AI 上下文管道做智能反馈。**

你的需求里，**统一数据模型、离线同步、信息流视图、AI上下文**四样是市面上没有任何现成方案能完整覆盖的，必须自建。但**PC追踪、位置、账本**三个重量级模块可以完全复用成熟开源项目，大幅降低开发成本。
