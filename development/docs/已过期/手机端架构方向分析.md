> 状态：此文为 2026-07-17 的历史分析稿。当前已落地的 Android 能力、位置记录语义和发布规则以 [`2026-07-19-Android阶段交接.md`](2026-07-19-Android阶段交接.md) 为准。

> 日期: 2026-07-17 | 作者: 巴蒂塔洛
> 背景: 真机实测一天后，发现当前架构存在根本性问题，需要重新审视方向

## 一、当前架构的根本问题

### 问题链

```
手机要采集数据 → 依赖 ActivityWatch 运行 → AW 在后台被系统杀
                                          → 用户必须手动保持 AW 前台
手机要发送数据 → 依赖 Tailscale VPN → TS 在后台也被杀
                                      → 用户必须手动保持 TS 运行
PC 要接收数据 → 笔记本休眠 → 端口不可达 → 数据发不出去
```

**结论：三个环节缺一不可，任何一个断了整条链就断了。** 这不是 bug，是架构选型的问题。

### 为什么 AW 和 TS 会被杀

Android 从 8.0 开始逐步收紧后台限制，到 12+ 已经非常激进：
- **普通后台服务**：Doze 模式下基本暂停，系统随时可杀
- **VPN 应用**（Tailscale）：Android 只允许一个 VPN 通道，且后台 VPN 进程优先级不高
- **第三方采集应用**（ActivityWatch）：依赖无障碍服务，但如果用户在系统设置里关了无障碍，AW 就废了

小米/华为/OPPO 等国产 ROM 比原生 Android 更激进，有自己的「省电策略」「自启动管理」「应用冻结」机制，即使开了无障碍也可能被杀。

### "后台上锁"能不能解决

礼程提到的安卓手机对后台应用上锁（小米的「锁定后台」、华为的「受保护应用」），原理是把这个应用加入厂商的白名单，降低被杀概率。**但这不等于保证不死**，只是降低概率。而且：
- 需要用户手动操作每个应用（AW、TS、Life Radio 三个都要锁）
- 不同厂商操作路径不同，没有通用 API
- 系统更新后可能重置白名单

## 二、两条可行路径

### 路径 A：自建采集，去掉 ActivityWatch 依赖

**核心思路**：我们的 App 自己用 `AccessibilityService` 监听应用切换，不再依赖 AW。

#### 技术方案

1. **数据采集层**：注册 `AccessibilityService`，监听 `TYPE_WINDOW_STATE_CHANGED` 事件
   - 每次前台应用切换时，记录：包名、Activity 类名、时间戳、持续时间
   - AccessibilityService 是系统级服务，优先级高于普通后台服务，被杀概率低
   - 开机自启：系统启动时已启用的无障碍服务会被自动绑定

2. **数据存储**：直接写入 Room 数据库（已有基础设施）

3. **网络传输**：去掉 Tailscale 依赖，改用直连 HTTP
   - PC 端服务器有公网 IP 或用内网穿透（如 frp、cloudflare tunnel）
   - 或者用老家电脑做常驻接收端（已有完善的远程控制）
   - 数据暂存本地，网络可达时批量上传

4. **后台保活**：AccessibilityService + 前台通知 + 请求忽略电池优化
   - 无障碍服务本身是系统级保活，比普通 foreground service 更难被杀
   - 配合 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 权限
   - 引导用户在系统设置里开启自启动

#### 优势
- **减少一层依赖**：不需要 AW 运行，App 自己就能采集
- **AccessibilityService 被杀概率最低**：系统视为辅助功能核心组件
- **数据更可控**：采集格式自己定义，不迁就 AW 的数据结构
- **已有代码基础**：`DataCollector.kt` 里已有 `collectAppUsageStats()` 用 UsageStatsManager 采集的逻辑，只是目前没被调用

#### 劣势/风险
- 需要用户在系统设置里开启无障碍服务（一次性操作）
- Google Play 对无障碍服务审核严格（但我们不上架 Play，自己 sideload 没问题）
- 小米等厂商可能在系统更新后关闭无障碍服务，需要监控+引导重新开启
- **开发量**：需要写 AccessibilityService、配置文件、引导 UI、保活逻辑

#### 采集精度对比

| 维度 | ActivityWatch 方案 | AccessibilityService 方案 |
|------|-------------------|------------------------|
| 应用切换事件 | ✅ 精确 | ✅ 精确（TYPE_WINDOW_STATE_CHANGED） |
| 持续时间 | ✅ 精确 | ⚠️ 需自己算（当前时间 - 上次切换时间） |
| 应用内页面变化 | ✅ 有 title | ⚠️ 只有 className，语义不如 title |
| 后台保活 | ❌ 依赖第三方 | ✅ 系统级服务 |
| 依赖数量 | AW + TS + Life Radio | Life Radio（网络用直连） |

### 路径 B：用现成的量化追踪 App

搜索结果中发现几个开源方案：

| 项目 | 类型 | 适用性 |
|------|------|--------|
| **Track & Graph** (F-Droid) | 习惯追踪+可视化，手动输入 | ❌ 不自动采集 |
| **aurboda** (GitHub) | 健康数据聚合，Health Connect | ❌ 偏健康指标，不含应用使用 |
| **openScale** | 蓝牙体重秤数据 | ❌ 不相关 |

**结论：没有现成的开源项目能替代我们的需求。** 市面上的量化追踪 App 要么偏健康数据，要么是手动输入，要么不开放数据接口。应用使用时长的自动采集 + 自定义服务器同步，目前没有开箱即用的方案。ActivityWatch 本身是这个领域最接近的，但它的后台保活问题在国产 ROM 上是硬伤。

## 三、网络传输方案重构

### 当前问题
Tailscale 是点对点 VPN，要求两端同时在线。PC 休眠 = 连接断开 = 数据丢失。

### 方案对比

| 方案 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| **A. 老家电脑做服务器** | 手机直连老家 PC 的公网 IP / 内网穿透 | 7x24 在线，远程控制完善 | 需要老家网络稳定 |
| **B. 云服务器中转** | 手机 → 云端 → PC 拉取 | 最可靠 | 需要租服务器，有月成本 |
| **C. 手机本地暂存 + PC 定时拉** | PC 醒着时主动从手机拉数据 | 不依赖手机主动推送 | 需要 PC 主动发起，手机端要开 HTTP 服务 |
| **D. 混合方案** | 优先直连 PC，失败则暂存本地，PC 可达时补传 | 最灵活 | 开发复杂度高 |

**推荐方案 D**，实现优先级：
1. 先做本地暂存（已有 Room 数据库，天然支持）
2. 网络可达时批量上传（已有逻辑，把 Tailscale IP 换成直连 IP 或域名）
3. PC 端用「龙虾助手」定时唤醒 → 唤醒后拉取数据

## 四、Token 使用反思

用户明确指出：
> "token 不能盲目使用，应该把它用在必要的地方，不能过高估计一定量的 token 能够开发的内容"

这是对的。回顾过去几天的开发：
- **有效投入**：v2.0 的 dataType 修复、AlarmManager 后台保活、PC 端按日期分割
- **高消耗低产出**：在模拟器上反复等 5-10 分钟验证后台同步（每次等待 = 大量 token 空转）
- **架构选型失误**：一开始就该评估 ActivityWatch + Tailscale 在国产 ROM 上的可行性，而不是直接写代码

### 下一步应该怎么做

1. **先想清楚再写代码**：架构方向确认后再动手，避免返工
2. **小步快跑**：每次只改一个东西，验证通过再改下一个
3. **减少等待验证**：模拟器上的长时间等待验证用 logcat 定时检查，不要 sleep 占用对话
4. **真机优先**：模拟器行为和真机（小米 Civi 4 Pro）差异大，尽早切真机

## 五、建议的行动计划

### 短期（立即可做，低 token 消耗）
1. **确认网络方案**：老家电脑能否做常驻接收端？公网 IP 还是需要内网穿透？
2. **手机后台上锁测试**：把 AW、TS、Life Radio 三个应用都锁定后台，观察能存活多久
3. **PC 防休眠**：设置电源管理，合盖不休眠（`powercfg /requestsoverride`）

### 中期（需要开发，控制 token）
4. **路径 A 实现**：在 Life Radio App 里集成 AccessibilityService，替代 AW 采集
5. **去掉 Tailscale 依赖**：改用直连 HTTP，目标地址可配置
6. **本地暂存 + 延迟上传**：网络不可达时数据存在 Room，可达时补传

### 长期
7. 位置数据采集
8. PC 端数据聚合 + AI 报告
