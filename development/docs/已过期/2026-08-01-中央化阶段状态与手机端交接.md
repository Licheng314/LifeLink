# Life Radio 中央化阶段状态与手机端交接

更新时间：2026-08-01

## 本阶段目标

把原来的 PC、手机和其他 PC 相互发现、互相转发，改造成统一的中央结构：

```text
PC 客户端 ──┐
             ├── HTTPS 中央服务 ── WebUI / AI
Android ─────┘
```

客户端只采集和上传本机数据；中央服务负责鉴权、去重、长期保存和统一读取。正式路径不再依赖 Tailscale，也不再进行多端发现或 PC 间广播。

## 已完成的工作

### 中央服务

- 已从 `pc-dashboard` 物理拆分到独立的 `central-server` 项目。
- 使用外部 SQLite 长期库存储设备、事件、批次和逐事件回执。
- 每个安装实例使用独立设备身份和独立上传凭据。
- 支持事件去重、批次幂等、持续事件 revision 更新和离线安全重试。
- 上传凭据只能写入本设备数据；AI/Web 读取使用单独的只读凭据。
- 已支持一行 `LR1...` 邀请文本：中央生成邀请，客户端粘贴并领取，随后保存自己的设备凭据。
- 花生壳 HTTPS 公网入口已验证健康检查、匿名拒绝、带凭据访问和真实事件写入。

### PC 客户端与 WebUI

- PC 客户端保留在 `pc-dashboard`，中央服务和客户端分别启动、分别退出、分别显示托盘图标。
- PC 从 ActivityWatch 采集本机应用、网站和 AFK 原始事件，先写本地 outbox，得到中央逐事件确认后再推进送达状态。
- 原有 WebUI 在中央模式下通过本机客户端代理读取中央数据，不接触中央只读 Token。
- 第二台真实 PC 已经通过中央邀请完成注册并连接到中央服务。
- 正式中央入口不会调用 Tailscale，也不会重新上传其他设备已经同步来的事件。

### Android 客户端

- 已实现中央模式所需的运行时服务地址、稳定 installation ID、加密 Token、本地队列、批量确认和离线退避。
- 应用用量与位置事件均已接入中央上传代码。
- 原 Tailscale 和多端发现不再属于正式手机同步路径。
- 已生成测试 APK：实际 `versionName 3.1`、`versionCode 22`。`app-debug.apk` 是默认文件名，不是版本号。

## 已验证的测试基线

- PC 客户端：86 项通过。
- 中央服务：50 项通过。
- 跨项目集成：10 项通过。
- 共享契约：14 项通过。
- Android：17 项通过，APK 构建成功。

这些结果证明代码层的鉴权、领取、上传、去重和回执机制具备自动化保障，但不能替代真实公网手机联调。

## 当前未完成与已知问题

### 1. Android 邀请领取仍返回 HTTP 400

真实手机粘贴中央邀请后，公网服务返回了旧校验错误：要求 `device_id` 必须是桌面 installation UUID。当前仓库中的新契约与服务代码已经允许 Android 使用同一套邀请协议，因此该现象更符合以下判断：

- 花生壳当前转发到的主机仍运行旧版中央服务；或
- 新代码已经复制过去，但实际监听 8091 的进程没有正确停止和重启；或
- 公网映射指向了另一台仍运行旧代码的电脑。

这不是“手机不能使用 PC 邀请密码”的产品限制。PC 与 Android 应使用同一个 `LR1` 协议，服务端按领取请求中的平台和能力登记设备。

### 2. 手机真实数据闭环尚未验收

领取问题解决后，必须分别确认：

- 应用用量能够写入中央库，应用名称和时长解析正确；
- 位置 observation 能写入中央库，并在服务端形成正确的位置/行程派生结果；
- 断网后重试不重复存储；
- WebUI 只出现一个稳定手机设备，不因名称、IP 或重装前数据产生重复卡片。

### 3. 中央读取面仍未完全迁移

当前 PC 用量读取闭环已经可用；位置页面和面向 AI 的全部摘要仍需继续迁移到中央只读接口。完成前，中央化版本仍属于联调阶段。

### 4. 兼容代码仍存在

旧 `legacy_p2p` 代码尚未完全删除，但已不是默认启动路径。应等 PC 与手机中央闭环稳定后再删除，避免调试期间同时进行大规模清理。

## 手机端开发对话接手范围

手机端对话接下来负责：

1. 确认花生壳实际指向的中央主机和监听 8091 的进程版本；
2. 更新并重启该主机的中央服务，重新领取一份未过期邀请；
3. 验证应用用量和位置数据的真实上传；
4. 修复 Android 端独有的领取、队列、权限或解析问题；
5. 保持 `versionCode` 单调递增，并为交付 APK 使用清晰的带版本文件名。

PC 端对话保留中央服务、PC 客户端、WebUI 与跨端契约的所有权；若手机端发现契约或服务端缺陷，应带上 HTTP 状态、响应正文、请求类型和复现步骤反馈回来。

## 启动与数据边界

- 中央服务：`central-server/start_server.bat`，默认监听 `127.0.0.1:8091`。
- PC 客户端：`pc-dashboard/start_central_client.bat`，本机 WebUI 默认位于 `127.0.0.1:8090`。
- PC 客户端运行状态：`%LOCALAPPDATA%\LifeRadio\client`。
- 中央服务运行状态：`%LOCALAPPDATA%\LifeRadio\central`。
- Android APK：`mobile-app/app/build/outputs/apk/debug/app-debug.apk`。

邀请文本、设备 Token、中央只读 Token 都是秘密，不应写入项目文档、聊天记录、契约 fixture 或 Git。曾经公开粘贴过的邀请应视为已暴露；若它尚未过期，也应废弃并重新生成。

## 下一阶段验收标准

1. 远端 PC 和真实 Android 都能通过同一邀请体系登记。
2. 两端离线后恢复网络，可以补传且不重复。
3. WebUI 按稳定设备身份展示 PC 用量、手机用量和手机位置。
4. 中央服务的 AI 只读入口可以输出统一的用量与位置摘要。
5. 达成上述闭环后再删除旧 P2P、Tailscale 和历史迁移兼容层。
