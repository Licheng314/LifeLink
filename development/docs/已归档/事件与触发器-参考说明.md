# 事件与触发器参考说明

状态：v1.13.2 现役参考；契约与中央自动化已通过，PC 前端调整与真实视觉/分钟调度已于 2026-08-16 验收通过；v1.13.2 修正晚睡在线检查为睡觉时间后每 30 分钟执行

更新时间：2026-08-17

## 1. 本文范围

本文集中说明中央事件时间线和触发器当前支持的字段、枚举、事件类型与判定机制。产品目的、心愿生命周期和 UI 原则仍以 [`心愿与事件系统-设计方案.md`](心愿与事件系统-设计方案.md) 为准；跨端 JSON 结构以 [`../../contracts/life-radio-api-v1.yaml`](../../contracts/life-radio-api-v1.yaml) 为最终契约。

背景摘要、系统里程碑、定时调度和目标文案已经按 [`事件需求总结.md`](事件需求总结.md) 接入 v1.13.2；本文记录当前代码机制，产品文字样本仍以该文档为准。

三个概念不能混用：

- **原始事件 `events`**：PC 或 Android 上传的高频事实，是长期数据来源。
- **时间线事件 `timeline_events`**：中央从重要事实或用户操作生成的低频、可读条目。
- **触发器 `event_triggers`**：用户在心愿内选择的中央预设判定配置；用户不能创造新的触发器类型。

原始事件不会因为时间线显示规则变化而删除。时间线也不会自动收纳所有原始事件。

## 2. 时间线事件公共字段

| 字段                    | 类型、枚举                                        | 示例                                         | 说明                                            |                              |
| --------------------- | -------------------------------------------- | ------------------------------------------ | --------------------------------------------- | ---------------------------- |
| `timeline_event_id`   | UUID 字符串                                     | `5bbd…`                                    | 中央生成的时间线记录 ID。                                |                              |
| `occurred_at`         | UTC `Z` 时间                                   | `2026-08-11T13:17:00Z`                     | 事实发生时间；WebUI 按共享 `Asia/Shanghai` 转换为 `21:17`。 |                              |

## 3. 当前时间线事件类型

### 3.1 心愿事件

| `event_key` | 机制 | `subject` 示例 | `evidence` 示例 |
| --- | --- | --- | --- |
| `wish.created` | 用户创建心愿时生成一次。 | `{"text":"每天早点睡"}` | `{"duration_days":3}` |
| `wish.period_completed` | 最后业务日结束且每日结果已填后，用户可手动完结；未处理则在 72 小时宽限后由中央惰性终结。两条路径均只生成一次。标题示例：`「每天早睡」心愿已完成`；详情示例：`完成的天数 2/3，再接再厉吧！` | `{"duration_days":3}` | `{"completed_days":2,"automatic_finalized":false}` |
| `wish.result_revised` | 已归档心愿的某日结果被改成不同值时，按修订次数生成。 | `{"business_date":"2026-08-10"}` | `{"completed_days":2,"duration_days":3}` |
| `wish.cancelled` | 旧版取消接口产生；新 PC/Android UI 已不再提供取消，只提供删除。 | `{}` | `{}` |

修改心愿文字不会生成时间线事件。删除心愿会删除纯心愿生命周期事件；已经真实发生的触发提醒继续保留，但解除心愿和触发器索引。

### 3.2 触发提醒事件

| `event_key` | 机制 | `subject` 示例 | `evidence` 示例 |
| --- | --- | --- | --- |
| `blacklist_usage_milestone` | 当前业务日黑名单用量达到配置周期时生成。 | `{"platform_scope":"all","milestone_minutes":60}` | `{"total_seconds":3720}` |
| `device_usage_milestone` | 指定设备的当前业务日设备使用时长达到配置周期时生成。 | `{"device_id":"desktop-…","milestone_minutes":60}` | `{"total_seconds":3680}` |
| `late_usage_milestone` | 晚间起始时间之后的周期时刻仍检测到前台使用时生成。 | `{"device_id":"all","milestone_index":2}` | `{"milestone_at":"2026-08-10T16:00:00Z","active_device_ids":["android-…"]}` |

### 3.3 设备投影事件

这两类先由客户端以 `custom.event` 原始事实上传，再由中央幂等投影到时间线：

| `event_key` | `category` | `importance` | 机制与示例 |
| --- | --- | --- | --- |
| `application.started` | `system` | `low` | Life Radio PC 客户端启动。新事件标题附中央设备名，详情附设备名和平台（例如 Windows）；`evidence` 保存原始 `event_id` 与平台。旧事件不改写。 |
| `sedentary.reminder_triggered` | `device` | `normal` | 久坐提醒实际触发，例如标题 `久坐提醒`；`evidence` 保存原始 `event_id`。 |

其他 `custom.event` 键不会自动进入时间线。

中央另生成 `system.ai_reader_connected` 与 `system.ai_reader_context_served` 两类 `system/low` 审计事件。它们在 WebUI 中默认灰色，仅供用户了解 AI 连接和中央成功提供上下文的事实。AI reader 接口统一排除所有 `importance=low` 事件；这些事件不参与空圈/对号读取标记。

### 3.4 固定系统里程碑与报告

这些类型由中央固定规则生成，不是用户可以创建或编辑的触发器类型：

| `event_key` | `importance` | 当前机制 |
| --- | --- | --- |
| `system.device_usage_milestone` | `normal` | 每台设备分别每满 60 分钟生成；PC 使用现役 AFK 裁剪口径。标题为“设备使用·设备名”，详情包含该设备应用/网站合并 Top 5。 |
| `system.blacklist_usage_milestone` | `normal` | 各平台先按自身规则隔离匹配，再全平台汇总，每满 30 分钟生成。 |
| `system.location_stay_milestone` | `normal` | 当前稳定地点连续停留每满 60 分钟生成；连续段身份进入去重键。 |
| `system.activity_duration_milestone` | `normal` | 连续步行、跑步或交通工具状态每满 30 分钟生成；状态切换后重新累计。 |
| `system.late_online_check` | `normal` | 睡觉时间后从 30 分钟开始每 30 分钟检查一次；只看检查点前 15 分钟的设备事实或心跳。 |
| `report.morning`、`report.evening`、`report.periodic` | `high` | 按共享设置的稳定分钟槽生成。早报读取前一业务日，晚报读取当前业务日，周期总结严格使用相邻槽位的 `[from,to)`；当前投送状态固定为 `not_configured`。 |

关联心愿的四种触发器只在该心愿冻结的 `starts_on..ends_on` 业务日期内运行；超过 `ends_on` 后即使心愿尚处于 72 小时待归档期也不再触发。

## 4. 触发器实例字段

| 字段 | 类型、枚举 | 示例 | 说明 |
| --- | --- | --- | --- |
| `trigger_id` | UUID | `986a…` | 中央触发器实例 ID。 |
| `wish_id` | UUID 或 `null` | `0bcc…` | 关联的活动心愿；数据结构允许全局触发器，但当前用户流程只在心愿内挂接。 |
| `trigger_type` | 枚举：`blacklist_usage_milestone`、`device_usage_milestone`、`late_usage_milestone`、`scheduled_reminder` | `scheduled_reminder` | 四种中央预设类型；用户不能创建新的触发器形式。 |
| `config_version` | 固定整数 `1` | `1` | 参数结构版本，不是用户可选项。 |
| `parameters` | 严格 JSON 对象 | `{"device_id":"all","start_local_time":"23:00"}` | 字段必须与对应类型完全一致，不能夹带未声明字段。 |
| `interval_minutes` | 枚举：`15`、`30`、`60`、`120` | `30` | 周期分钟数；不是冷却时间。 |
| `enabled` | 布尔值 | `true`、`false` | 是否参与判定。关闭后保留配置和历史事件。 |
| `created_at` | UTC `Z` 时间 | `2026-08-11T12:00:00Z` | 实例创建时间。 |
| `updated_at` | UTC `Z` 时间 | `2026-08-11T13:00:00Z` | 参数、周期或启用状态最近变更时间。 |
| `last_triggered_at` | UTC `Z` 时间或 `null` | `2026-08-11T13:17:00Z` | 最近一次实际新增提醒事件的判定时间；从未触发则为空。 |

创建请求另有 `request_id`（UUID，例如 `447c…`），用于幂等重试；它不出现在最终触发器读取对象中。

## 5. 四种触发器的已实现机制

### 5.1 黑名单用量里程碑

- 参数只有 `platform_scope`，枚举为 `all`、`pc`、`android`、`web`；客户端默认 `all`。
- `pc` 只统计 PC 应用规则，`android` 只统计 Android 应用规则，`web` 只统计网站规则。
- `all` 是把三个平台各自完成隔离匹配后的结果相加，不会让一条 PC 黑名单规则跨到 Android 命中。
- 应用名称采用不区分大小写的子串匹配；网站采用域名等值或子域匹配。
- PC 应用用量沿用前台区间减去明确 AFK 重叠的中央口径；Android 保持应用前台用量。
- 周期可选 `15/30/60/120` 分钟。例如周期 60 分钟，正常运行时在累计达到 60、120、180 分钟时分别产生提醒。

### 5.2 设备用量里程碑

- 参数只有 `device_id`，例如某台 PC 或手机的稳定中央设备 ID。
- 只累计该设备在当前业务日内的设备使用时长。
- PC 使用合并后的前台区间，并剪去明确 AFK；重叠窗口不会重复累计。
- Android 使用应用前台事件，当前没有与 PC ActivityWatch 等价的 AFK 信号。
- 周期可选 `15/30/60/120` 分钟。

### 5.3 晚间使用里程碑

- 参数为 `device_id` 和 `start_local_time`。
- `device_id` 可以是稳定设备 ID，也可以是保留值 `all`；客户端默认 `all`，表示任一设备。
- `start_local_time` 使用 `HH:MM`，例如 `23:00`；它按中央共享业务日解释，可以跨自然日。
- 周期可选 `15/30/60/120` 分钟。例如 `23:00 + 30分钟周期`，检查时刻为 23:30、00:00、00:30……
- 在周期检查点只判断此前 15 分钟内是否存在该设备的可验证事实或心跳；它不是累计在线时长，也不要求存在前台用量。`all` 表示任一设备符合即可。

### 5.4 心愿定时提醒

- 类型为 `scheduled_reminder`，参数只有 `reminder_local_time`（`HH:MM`）；内部兼容字段 `interval_minutes=1` 不向用户展示。
- 每个心愿固定业务日按该心愿创建时冻结的跨日设置解释本地时间；早于跨日小时的钟表时间落在下一自然日。
- 心愿已完结、已删除或提醒关闭时不触发；错过目标时间超过 15 分钟不补发。
- 标题以 `心愿提醒·` 开头，`importance=high`；详情不重复该前缀。

### 5.5 配置变更和过期提醒

目标口径是：创建、修改或重新启用触发器时，以该配置的生效时刻作为新基线，不补发此前已经越过的周期。一次判定跨过多个周期时只保留当前最新有效里程碑，避免离线补传或改配置后突然出现一串过期提醒。

该口径只影响后续派生，不自动删除或改写已经进入中央时间线的事件。

## 6. 查询与筛选

中央时间线按 UTC 半开区间查询，并按 `occurred_at` 从近到远返回。现有筛选字段为：

- `category`：枚举 `wish`、`trigger`、`device`、`user`、`system`；例如只读提醒使用 `category=trigger`。
- `importance`：枚举 `low`、`normal`、`high`；例如只读高重要性事件使用 `importance=high`。
- `wish_id`：指定心愿 UUID，例如只查看某条心愿关联的事件。

早报、晚报和定时总结仍会生成时间线事件，并保留同一事件上的 `delivery.state=not_configured` 兼容展示；它不表示 AI 读取状态。v1.15.3 由唯一有效 AI reader 的游标和访问日志动态计算“待推送/已推送”，见 `AI接入方案-评估.md`。

## 7. 原始事件与时间线的关系

中央接受的原始 `event_type` 枚举目前包括：

| 原始类型 | 示例 | 是否自动进入时间线 |
| --- | --- | --- |
| `app.foreground` | PC 前台窗口、Android 应用前台区间、ActivityWatch AFK/Web 事实载荷 | 否；只参与用量和触发器派生。 |
| `custom.event` | `application.started` | 仅白名单中的启动和久坐提醒会进入。 |
| `calendar.event` | 日历安排 | 否。 |
| `task.update` | 任务状态变化 | 否。 |
| `location.observation` | Android 位置观察 | 否。 |
| `location.sample` | 兼容位置采样 | 否。 |
| `location.stay` | 位置停留段 | 否。 |
| `location.visit` | 兼容位置访问段 | 否。 |
| `manual.note` | 手动笔记 | 否。 |

因此“中央保存了某种原始事实”不等于“事件时间线一定展示它”。新增位置到达/离开等时间线类型时，应先定稿事件键、去重和发生时间语义，不能直接把高频位置观察整批展示出来。
