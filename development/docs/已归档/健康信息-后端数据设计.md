# 健康信息：后端数据与派生设计

更新时间：2026-08-13  
状态：步数/睡眠原始派生接口继续兼容；活动状态、区间代表位置及主手机选择由 v1.11.1 和《活动状态-中央派生与WebUI设计》接管

## 1. 目标与边界

“健康信息”是中央服务提供的一组参考指标，首期包含：

1. **睡眠参考**：综合 Android 与 PC 的明确交互事实，估算过去一夜的主要休息区间。
2. **步数统计**：Android 上传计步传感器累计值观察，中央按设备和日期计算增量。

这两项均不是医疗数据。系统不得宣称真实入睡、醒来、睡眠阶段、睡眠质量或医学意义上的运动量。

首期不做：

- 不接入 Health Connect、Google Fit、手环或云厂商健康平台；
- 不增加睡眠结果表或步数日汇总表；
- 不把派生结果作为原始事实永久固化；
- 不把多个手机的步数直接相加；
- 不增加健康提醒、评分、排行榜或 AI 主动发送；
- 不在本阶段实现 WebUI 视觉排版。

## 2. 权威数据与数据流

```text
PC app.foreground + ActivityWatch AFK ──┐
                                        ├── 中央动态派生 ──> GET /v1/health-info
Android app.foreground ─────────────────┘                       │
                                                                ├──> PC WebUI 健康信息页签
Android health.steps_observation ─────────> 中央长期事件库 ─────┘
                                                                └──> Android 健康信息
```

- 原始 `app.foreground`、AFK 和 `health.steps_observation` 进入中央 `events` 长期库。
- 睡眠和每日步数在读取时动态计算；算法变化后允许从原始事实重算历史。
- Android 本地 Room 只承担采集队列和断网重试，不是跨设备健康结果权威。
- PC 浏览器以后仍通过本机代理访问，不接触中央凭据。

## 3. 统一读取接口

首期新增：

```http
GET /v1/health-info?date=YYYY-MM-DD
```

`date` 表示本地醒来日期/统计日期，按中央共享 `timezone=Asia/Shanghai` 解释。读取接受独立只读 Token 或已注册设备 Token；没有写接口。

早报必须区分日期口径：昨日用量和昨日步数读取前一日，标题为“昨夜健康”的睡眠参考则读取早报当天，因为睡眠 `date` 表示醒来日期。不得把三者统一使用前一日，否则会把前一晚的睡眠重复写入今日早报。

## 4. 睡眠参考语义

### 4.1 夜间窗口

- 以请求 `date` 为醒来日期。
- 固定观察窗口为前一自然日 21:00 到该日 12:00，使用中央共享时区换算为 UTC。
- 当查询正在进行中的当夜且尚未到 12:00，`window_end` 截止当前时间。
- 12:00 只是最晚观察边界，不是睡眠结束时间，也不是结果完成时间。
- 尚未出现足以闭合主要无交互区间的醒后使用时，返回 `status=estimating`。
- 一旦后续真实使用闭合当前最长候选区间，立即返回 `status=final`；不需要等到 12:00。
- 到 12:00 仍无法形成双侧闭合证据时返回 `insufficient_data`。

首期夜间窗口不复用业务日 `day_start_hour`。业务日用于日常统计，睡眠窗口用于跨午夜休息观察，二者语义不同。

### 4.2 明确交互区间

- Android：使用 `app.foreground` 区间。
- PC：只采用前台 window 与明确 ActivityWatch `status=not-afk` 区间的交集。
- PC 的程序运行、设备在线、中央服务运行或缺少 AFK 事实不算用户交互。
- 所有设备区间先裁剪到夜间窗口，再按时间取并集；同一时刻多设备活动不重复累计。

### 4.3 估算规则

1. 从设备交互并集中提取不少于 1 小时的无交互间隙。
2. 相邻两个大间隙之间的整段使用/短空档跨度不超过 30 分钟时，将它们连接为同一候选；可以连续连接多次。候选内真实交互秒数累计到 `interruption_seconds`，不得计入 `rest_seconds`。
3. 按旧 Android 算法选择 `interval_seconds`（合并后区间跨度）最大的候选；`rest_seconds` 作为扣除真实交互后的辅助值，不负责改变主候选。
4. 只有同时存在睡前活动边界与醒后活动边界时，才能产生闭合的 `estimated_start` / `estimated_end`。
5. 没有事件、只有单侧证据或覆盖不足时，在窗口进行中返回 `estimating`，窗口结束后返回 `insufficient_data`；不能把完整 `21:00→12:00` 当作睡眠。
6. `estimated_start` 是睡前最后一段明确使用的结束时刻；`last_activity_devices` 是为该边界提供证据的设备。
7. `estimated_end` 是闭合候选区间的醒后第一段明确使用的开始时刻；`first_activity_devices` 是该时刻实际使用的设备。
8. `finalized_at` 与当前结果的 `estimated_end` 相同，表示这次醒后使用在真实世界发生的时间；不得使用接口查询时间、中央入库时间或 12:00。
9. `interval_seconds = estimated_end - estimated_start`，表示页面上的睡眠估算区间跨度；`rest_seconds` 排除区间内不超过 30 分钟的短暂使用，`interruption_seconds` 单独展示。三者不得混用。
10. 结果由原始事件动态重算。若稍后证据表明先前醒后使用只是一次不超过 30 分钟的夜间中断，中央会把同一主要区间延伸到下一次闭合边界，并相应更新 `estimated_end`、`first_activity_devices` 与 `finalized_at`；不把旧结果固化为第二份事实。

状态枚举：

| 状态 | 含义 | 示例 |
| --- | --- | --- |
| `estimating` | 观察窗口仍在进行，且尚无醒后使用闭合主要候选 | 凌晨 02:00 仍未使用任何设备 |
| `final` | 已由醒后最早真实使用闭合当前主要区间 | 06:20 首次使用手机后形成 23:05→06:20 |
| `insufficient_data` | 到 12:00 仍无法形成可靠双侧证据 | 手机没同步且 PC 无 AFK 事实 |

## 5. 步数原始事件与统计

### 5.1 原始事件

新增事件类型：`health.steps_observation`。

```json
{
  "event_type": "health.steps_observation",
  "occurred_at": "2026-08-12T08:00:00Z",
  "source": {
    "kind": "android",
    "collector": "step_counter",
    "reliability": "observed"
  },
  "payload": {
    "counter_value": 123456,
    "counter_session_id": "4d7acb63-bbed-41a9-aaeb-00fcb6f35a38",
    "sensor_type": "android.step_counter"
  }
}
```

- `counter_value` 是非负整数，表示当前计数周期内传感器累计步数。
- `counter_session_id` 是客户端生成并持久化的 UUID；检测到计数值下降、设备重启或传感器重置时必须生成新值。
- 观察事件不可变；事件 ID 对同一次本地观察稳定，重试不得制造副本。
- Android 10 及以上必须声明并由用户授予 `ACTIVITY_RECOGNITION`。用户拒绝后保持未启用，不循环弹窗。

### 5.2 中央差分

- 只对同一 `device_id` 的时间相邻有效观察做差，且两者 `counter_session_id` 必须相同；session 切换或无效观察都会断开基线。原始事件不被改写。
- 有效非负差值全部归入**后一个**观察转换到 `Asia/Shanghai` 后的自然日和本地小时（`0` 至 `23`）。即使两次观察跨越一个或多个小时，也不拆分、不丢弃；跨午夜同样只归后一个观察所在日。
- 差值为负、字段非法或跨 session 时不计步；负差值与日内发生的非法观察写入 warning。
- 每台 Android 设备返回自己的步数、样本数、覆盖范围和 `hourly_steps`。`hourly_steps` 始终恰好 24 个非负整数，索引对应 Asia/Shanghai 本地小时；`available` 时 24 项之和严格等于 `steps`，`insufficient_samples` 时固定返回 24 个零且 `steps=null`。
- 多台手机不得自动求和。前端在只有一个有效来源时可以突出该值；多个来源必须按设备展示。
- 没有权限、没有传感器、没有样本和样本不足是不同状态，不能都显示为 0 步。

步数状态枚举：

| 状态 | 含义 | 示例 |
| --- | --- | --- |
| `available` | 存在同 session 的有效差分 | 6421 步 |
| `insufficient_samples` | 只有一个样本，无法求差 | 刚启用采集 |
中央响应首期只有 `available` 与 `insufficient_samples`。`permission_required` 和 `sensor_unavailable` 是 Android 本地诊断状态，不进入中央枚举，也不为此制造伪造的零步事件。

客户端若需选择一个默认步数设备，必须先选择 `available`，再按 `sample_count` 最大、`last_sample_at` 较新、`device_id` 稳定字典序的顺序决胜；不能把多设备步数相加。

## 6. 前端页签边界

PC WebUI 的“健康信息”页继续消费完整 `/api/health-info?date=...`：

- 今日卡按手机设备展示当日总步数和覆盖状态；
- 本周图按周日到周六展示已抵达日期的每日总步数；
- 保留昨晚睡眠卡与本周睡眠区间图；删除的只有旧小时步数分布图。
- 分钟活动状态图已迁入“位置轨迹”，具体口径见 [`活动状态-中央派生与WebUI设计.md`](活动状态-中央派生与WebUI设计.md)。

Android 健康页读取同一中央结果，至少显示昨晚区间、区间跨度、睡前/醒后设备和按手机拆分的当日步数。断网时可以展示最近一次只读缓存并明确标记“当前离线中”，不继续使用手机本地睡眠算法形成另一套权威结果。Android 本期不要求七日图表。

## 7. 验收边界

自动化至少覆盖：

- PC window 与 `not-afk` 交集，AFK/缺失 AFK 不误报活动；
- 手机夜间活跃能打断 PC 空闲，PC 活跃能打断手机空闲；
- 多设备重叠交互只算一次；
- 空数据、单侧边界和当前夜晚状态；
- 跨午夜步数观察、session 重置、负差值、重复上传和多手机不求和；
- 只读 Token 与设备 Token 可读，匿名请求 401；
- 原始事件写入失败不产生派生结果，派生失败不改写原始事件。

真实设备验收必须分别记录：Android 权限与传感器回调、后台采样、中央步数递增、PC/手机夜间交互共同影响同一睡眠结果，以及 WebUI/Android 显示一致。
