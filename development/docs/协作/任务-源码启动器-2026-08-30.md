# 任务：源码启动器试验

状态：代码、专项验证与本机构建验证已完成。

- 目标：为中央服务和 PC 客户端分别提供正式名称与图标的源码开机启动入口，并在首次双击模块批处理时准备缺失的 Python 环境、PyInstaller 与本模块启动器。
- 不做：不打包中央或 PC 项目本体，不构建 MCP EXE，不改变身份、数据库、协议或用户数据位置。
- 修改范围：两个模块批处理、`development/tools/` 初始化与构建脚本、模块根目录启动器、两个 Windows 启动登记模块、对应测试和模块 README。
- 数据来源：启动器从自身位置解析项目根目录；用户数据仍只在 `%USERPROFILE%\LifeLink`。
- 验收：两个 EXE 可独立启动对应源码；启动项分别指向两个 EXE；项目内不产生新运行数据。
- 风险：中。项目移动会使 Windows 快捷方式旧绝对路径失效；下一次手动启动源码会刷新它。

归属口径：启动器不是第三个项目，也不保存数据或产生设备身份；它只是所属模块的 Windows 启动入口。源码和 EXE 分别放入 `central-server/`、`pc-dashboard/` 根目录；构建脚本保留在 `development/tools/`。两个 Windows 启动快捷方式已分别直接指向所属模块内的 EXE。根目录 `launchers/` 试验目录已清除。

首次启动口径：仅在对应模块 EXE 不存在时，初始化器才创建 `%USERPROFILE%\LifeLink\tools\build-python`、安装 `requirements-build.txt` 中的 PyInstaller 并构建该模块 EXE；正常重复启动不访问 pip。Python 3.13 缺失时先征得用户同意，再使用 `winget` 安装。MCP EXE 保持延后构建。

验证：两个角色均以 `bootstrap_windows.ps1 -NoStart` 通过真实环境检查，未启动服务；`build_source_launchers.ps1 -Target all` 已成功生成两个模块 EXE，且已用 Windows PowerShell 5 重新构建中央启动器并通过脚本解析检查。尚未在一台完全没有 Python、PyInstaller 与启动器的 Windows 用户环境完成端到端人工验收。
